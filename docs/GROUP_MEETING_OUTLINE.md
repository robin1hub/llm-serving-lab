# LLM Serving教学模拟器：设计与当前进展

组会汇报提纲｜2026-10-16｜建议5页，约5分钟

项目地址：https://github.com/robin1hub/llm-serving-lab

汇报主线：为什么做 → 如何模拟 → 单卡能力 → 多卡流程 → 校准与下一步。

## 第1页：为什么做这个模拟器

### 页面内容

**目标：理解LLM Serving的执行过程，为后续调度实验提供工具。**

- 观察请求从到达、排队、Prefill到Decode完成的全过程。
- 通过配置batch策略、KV容量和执行耗时，比较性能变化。
- 从单卡逐步扩展到多卡，最终研究D侧高压力下的调度。

### 简短讲稿

最初做这个项目是为了理解LLM Serving。我们把请求、组batch、KV管理和时间推进拆成可观察的过程，再逐步扩展到多卡。模拟器不执行真实模型，而是模拟执行耗时与资源状态，因此可以方便地修改配置、检查调度行为。

## 第2页：模拟器的整体架构

### 页面内容

```text
配置文件＋请求负载
        ↓
全局事件队列：请求到达、计算完成、传输开始/完成、worker唤醒
        ↓
      Worker
 ┌─────────────────────────────────┐
 │ Scheduler：选择这一轮的请求和阶段 │
 │ KV管理器：容量检查、块预留与释放  │
 │ Predictor：估计本轮batch执行耗时  │
 └─────────────────────────────────┘
        ↓
更新请求与资源状态，安排下一事件
        ↓
输出执行轨迹和性能统计
```

**Scheduler决定跑什么，Predictor决定跑多久，事件队列决定时间怎么推进。**

### 简短讲稿

模拟器采用离散事件方式，不需要每毫秒扫描一次系统。在worker可以执行时，调度器选择候选batch，检查KV容量，再由Predictor估计耗时并安排完成事件。到完成时更新token、KV和请求状态，继续下一轮。多卡共用一个事件队列，但每张卡的队列、调度状态和KV池相互独立，所以不同卡可以并行执行。

## 第3页：单卡已经能模拟什么

### 页面内容

| 机制 | 当前能力 |
| --- | --- |
| 动态组batch | 请求可逐轮加入或完成退出，受请求数和token预算限制 |
| Chunked Prefill | 长输入拆成多个块，分轮执行 |
| 混合batch | 支持一个Prefill块与多个Decode请求同轮执行 |
| KV Cache | 分页块分配、容量准入、填充、就绪与释放 |
| 容量恢复 | Mix模式支持抢占和重算 |
| 选批策略 | Prefill优先、Decode优先、阶段交替和混合执行 |

混合batch组成示意（不表示实测时间）：

```text
本轮batch = A的一个Prefill块 + B的一个Decode token + C的一个Decode token
                       ↓
               Predictor估计整轮耗时
                       ↓
               完成后更新各请求进度
```

### 简短讲稿

现在已经不是一个请求完整执行完再处理下一个。Prefill可以分块，Decode请求每轮生成一个token，并可与一个Prefill块组成混合batch。调度时既要满足人数和token预算，也要检查KV是否放得下。不同优先级策略会改变TTFT和生成间隔，可以直接比较它们的取舍。

## 第4页：多卡模拟到了哪一步

### 页面内容

- 支持多个独立Mix worker，使用固定请求归属。
- 支持固定1P1D：P完成Prefill并产首token，KV传到D后继续生成。
- 链路带宽、固定延迟、每token KV字节数均可配置。
- 传输期间保留源KV，目标Ready后才能继续Decode；复制可与其他计算重叠。

教学示例：输入4个token，输出3个token。

| 阶段 | 时间区间 | 发生什么 |
| --- | --- | --- |
| P侧Prefill | 0–8ms | 处理输入，在8ms产首token |
| KV传输 | 8–13ms | 传输4096字节KV，目标完成后就绪 |
| D侧第一轮 | 13–15ms | 在15ms产第二个token |
| D侧第二轮 | 15–17ms | 在17ms产第三个token |

**输出时间：8、15、17ms；生成间隔：7、2ms。首个间隔包含KV传输。**

### 简短讲稿

这个例子用于核对多卡时间线。P在8毫秒产首token，随后KV传输花5毫秒，D再花2毫秒产生下一个token，所以中间出现7毫秒间隔。它说明传输不是独立于请求指标的额外数字，而会影响用户看到的生成节奏。这里使用的是教学参数，不能当作4090实测速度。

当前边界：尚未实现运行中D→P迁移、动态目标选择，以及PD目标KV容量不足时的等待协议。

## 第5页：校准、输出与下一步

### 页面内容

**输入与输出**

- 输入：本地ShareGPT分词后的请求长度、明确的到达时间，以及独立实验配置。
- 输出：执行/传输轨迹、TTFT、ITL、请求延迟、吞吐及KV状态记录。

**已有校准**

- 在4090和A6000上测量过Qwen2.5-3B相关模型的执行轮耗时。
- A6000用纯Prefill/Decode数据拟合参数，冻结后验证混合batch。

| 验证范围 | 平均绝对百分比误差 | 最大误差 |
| --- | --- | --- |
| A6000：9组“1个P块＋多个D请求”，共180个目标轮 | 5.64% | 10.35% |

适用边界：特定模型、硬件、同步eager执行与batch形状；不是所有负载的精度保证。多卡端到端请求与链路尚未实测验证。

**下一步**

1. 补齐目标KV不足时的等待与恢复协议。
2. 实现运行中D→P迁移，以及P侧接纳外来Decode。
3. 用简单策略建立基线，再研究D-heavy条件下的迁移选择与参数优化。

### 简短讲稿

耗时预测已经做过初步校准。这里展示的是A6000受控混合batch的结果，混合数据没有用于拟合。但这个误差只代表特定执行轮，不代表完整请求和跨卡传输已经准确。下一步先补齐迁移所需机制，确认什么情况下迁移有收益，再比较调度策略。
